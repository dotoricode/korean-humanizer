## Step-by-step 체크리스트

### Step 1 — Google Form 만들기 (10 분, 사용자 직접)

1. [Google Forms](https://forms.google.com) 새 폼 생성.
2. [`docs/beta-feedback-form-spec.md`](beta-feedback-form-spec.md) 의 7 개 필수 + 2 개 선택 질문 그대로 복사.
3. 응답 수집 시트 자동 생성 옵션.
4. **공유 가능 링크** 생성 (응답 권한: 누구나).
5. 폼 링크를 [`docs/beta-guide.md`](beta-guide.md) 의 "🔗 [피드백 폼 링크]" 자리에 PR 로 추가.
6. 본인이 테스트 응답 1 회 — 시트 column 이 spec 과 매칭 확인.

### Step 2 — 베타 모집 (1 주 calendar, 사용자 직접)

[`docs/beta-recruit.md`](beta-recruit.md) 의 채널별 모집 글 사용:

- [ ] **X / Threads** — 한국어 + 영어 트윗 게시 (한 시간 간격, 같은 트윗에 reply)
- [ ] **IndieHackers KR Slack** — 한국어 모집 글 게시
- [ ] **한국어 작가 디스코드 / 글쓰기 커뮤니티** — 모집 글 (있는 경우)
- [ ] **개인 네트워크** — 작가 / 마케터 / 글 자주 쓰는 지인 1-2 명 DM (가장 안정적)
- [ ] **GitHub Issue 템플릿** — `.github/ISSUE_TEMPLATE/beta_signup.md` 추가 (선택, 신청 표준화)

**목표**: 3-5 명 confirmed.

**분기 시나리오**:
- 3 명 이상 → 정규 일정 (3 주) 진행
- 1-2 명 → RC 기간 1 주 연장 (rc.2 / rc.3)
- 0 명 → 본인 + 지인 1 명으로 1 주 → RC publish → 6-8 주 RC 기간

### Step 3 — 베타 운영 (1-2 주 calendar, 사용자 직접)

각 베타 사용자에게:

- [ ] 환영 메시지 — `docs/beta-guide.md` 링크 + Google Form 링크 + 일정 안내
- [ ] 환경별 설치 도움 (막히는 분 1:1 — Claude Code / Claude.ai / ChatGPT 등)
- [ ] **Day 3 first check-in** — 첫 humanize 인상 짧게
- [ ] **Day 7 mid check-in** — 사용 빈도 / 막힌 부분
- [ ] 매일 폼 응답 체크 — Q5 (의미 보존) ≤ 2 = critical bug → 24 시간 내 컨택
- [ ] 응답 매번 정리 (`docs/beta-feedback.md` 신규 — 익명화 후 누적)
- [ ] **Wrap-up 메시지** — "이번 주말까지 마지막 폼 응답 부탁"

### Step 4 — 피드백 분석 + 룰 미세 조정 (1-2d, 메인테이너 또는 협업)

- [ ] `docs/beta-feedback.md` raw 응답 → 4 카테고리 분류:
  - 누락 패턴 → 카탈로그 행 추가 (12 카테고리 freeze 안에서)
  - 과교정 → 빈도 컬럼 high → med 조정
  - 도메인 톤 위반 → 부록 E 우선순위 조정
  - Brand voice 한계 → 4 번째 mode 보강
- [ ] PR 1-3 개 머지 — 각각 single-issue 형태로 (review 가능)
- [ ] 각 PR 의 변경이 freeze 영역 (`docs/STABILITY-PROMISE.md`) 안에 머무는지 확인
- [ ] freeze 영역 깨야 하면 → v1.1 / v2 트랙으로 미루고 v1.0 에서는 *현재 룰* 안정화

### Step 5 — v1.0.0-rc release (1 일, 사용자 직접)

- [ ] 모든 lint 4 종 + eval-harness 통과 확인
- [ ] CHANGELOG.md `[1.0.0-rc.1]` 섹션 추가 — 베타 피드백 반영 PR 목록 + breaking 명시
- [ ] git tag:
  ```bash
  git tag -a v1.0.0-rc.1 -m "v1.0.0-rc.1 — beta feedback applied, freeze candidate"
  git push origin v1.0.0-rc.1
  ```
- [ ] GitHub release 생성 — release notes 에 CHANGELOG 1.0.0-rc.1 섹션 + MIGRATION 링크
- [ ] 베타 사용자에게 RC 알림 + 1 주 confirmation 요청
- [ ] RC 기간 (1 주 이상) 동안 critical bug 발견 시 1.0.0-rc.2 / rc.3 반복

### Step 6 — v1.0.0 GA release (0.5 일, 사용자 직접)

RC 기간이 깨끗하게 끝나면:

- [ ] CHANGELOG.md `[1.0.0]` 섹션 — `[1.0.0-rc.1]` 와 동일 내용 + RC 기간 동안의 hot-fix
- [ ] README hero 의 status 배지 `v1.0--rc` → `v1.0.0` 갱신
- [ ] `docs/STABILITY-PROMISE.md` 날짜 명시 (v1.0 release 일자)
- [ ] git tag:
  ```bash
  git tag -a v1.0.0 -m "v1.0.0 — first stable release"
  git push origin v1.0.0
  ```
- [ ] GitHub release 생성 — release notes 에 CHANGELOG 1.0.0 + MIGRATION 링크 + 베타 사용자 감사
- [ ] **베타 사용자 README contributor 섹션 추가** — 동의자만 표기 (폼 Q10)
- [ ] (선택) 트윗 / LinkedIn / HackerNews 공지

### Step 7 — Wiki 갱신 (0.5 일, 사용자 직접)

- [ ] GitHub Wiki — v1.0 release notes 페이지
- [ ] v0.5-v1.0 4 sprint 변경사항 종합
- [ ] STABILITY-PROMISE / MIGRATION / SECURITY 빠른 링크

### Step 8 — 핸드오프 마무리 (0.5 일)

- [ ] ROADMAP.md S4 status `진행 중 (RC 직전 상태)` → `✓ 완료 (v1.0.0 release)` + 일자
- [ ] v1.0 이후 1.x 후속 후보 명시 (LLM-as-judge / Batch / Brand voice 자동 추출 / 추가 도메인 / 빈도 재라벨링)
- [ ] 메모리 갱신 — v1.0 freeze 영역 reference (`memory/v1_freeze_areas.md` 신규)
- [ ] `docs/v1.0-handoff.md` (이 문서) — 모든 체크박스 ✓ 후 archive 또는 삭제

## 베타가 막히면 (Plan C)

3 명 이상 모집 못 하고 0 명 confirmed 라면:

1. 본인 + 지인 1 명으로 1 주 사용 → critical bug 없으면
2. **v1.0.0-rc 분리 publish** (베타 사용자 0 명이라도 RC tag)
3. RC 6-8 주 기간 동안 자연 사용자 유입 대기 — GitHub watch / star 가 1 명 이상이면 그 사람들도 베타 사용자로 invite
4. 8 주 후 critical bug 0 이면 v1.0.0 GA 자동 promotion

이 시나리오에서도 freeze 약속은 유효. v1.0 출시 후 1.x 트랙에서 누적된 베타 피드백 / 사용자 issue 를 minor 로 반영.
