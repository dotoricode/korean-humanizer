# 한국어 AI 글쓰기 "AI 티" 체크리스트

> Korean AI writing tells — 입력 텍스트에서 아래 패턴이 보이면 더 자연스러운 대안으로 바꾼다.

**과교정 방지 룰**:
- 한 문단에 **3곳 이상**은 건드리지 않는다.
- **전체 문장 수의 20%** 이상은 수정하지 않는다(예: 20문장 글이면 최대 4문장만 손댄다).
- 1-3문장짜리 짧은 글은 20% 계산 대신 **최대 1문장 / 문장당 1-2표현**만 고친다.
- 팩트 / 숫자 / 고유명사 / 인용문 / 링크는 **절대** 변경하지 않는다.
- 살짝 덜 매끄러운 게 더 사람답다. 과도한 세련미는 오히려 AI 티.

## 1. 강조어 남발 (Empty Intensifiers)

AI는 모든 게 "매우 / 정말 / 굉장히 / 획기적"이다. 실제로는 대부분 평범하다.

| 나쁨 | 자연스러움 | 빈도 | 적용 도메인 |
|---|---|---|---|
| 매우 중요한 | 중요한 / 꽤 중요한 | high | all |
| 정말 효과적인 | 효과적인 / 실제로 도움되는 | high | all |
| 굉장히 획기적인 | 새로운 / 눈에 띄는 | med | marketing,review |
| 매우 유용한 | 쓸만한 / 실제로 쓰이는 | med | marketing,review |
| 엄청난 | 큰 / 꽤 / (구체 수치로) | med | marketing,review |
| 한층 더 | 더 / (삭제) | high | marketing,linkedin |
| 더더욱 | 더 / 훨씬 | med | marketing,linkedin |
| 보다 ~한 | 더 ~한 ("보다"는 비교 대상이 명시될 때만) | med | all |
| 너무나도 | 너무 / (삭제) | med | all |

## 2. 공허한 형용사 (Empty Adjectives)

구체성이 없는 꾸밈말. 빼거나 구체로 바꾼다.

| 나쁨 | 자연스러움 | 빈도 | 적용 도메인 |
|---|---|---|---|
| 다양한 방법 | 몇 가지 방법 / 세 가지 방법 | high | all |
| 폭넓은 경험 | 긴 경험 / 5년 이상 경험 | med | linkedin,b2b-message |
| 혁신적인 솔루션 | 새 방식 / (구체 기능 명시) | high | marketing,review |
| 효과적인 전략 | 실제로 먹히는 전략 / (성과 수치) | high | marketing,b2b-message |
| 체계적인 접근 | 순서대로 / 단계별로 | med | formal |
| 광범위한 분야 | 여러 분야 / (구체 영역 나열) | med | all |
| 포괄적인 가이드 | 전체 가이드 / 처음부터 끝까지 | high | blog,newsletter |
| 종합적인 분석 | 전체 분석 / 모아서 본 분석 | med | academic,news |
| 전반적인 흐름 | 전체 흐름 / 큰 흐름 | med | all |
| 특별한 의미 | (구체) / 남다른 의미 | med | all |
| 의미 있는 변화 | (어떤 변화인지 구체) | med | all |
| 가치 있는 시도 | (어떤 가치인지 구체) | med | all |

## 3. 과격식 / 번역체 (Translation-ese & Stiff Formalism)

영어 / 일본어 직역 흔적, 격식체 남용.

| 나쁨 | 자연스러움 | 빈도 | 적용 도메인 |
|---|---|---|---|
| ~에 대해 말씀드리자면 | ~에 대해 얘기하면 / (바로 본론) | med | email,b2b-message |
| 다음과 같습니다 | (바로 내용으로) | high | formal |
| 저는 ~입니다. 저는 ~합니다. | (주어 생략) | med | all |
| ~라는 것입니다 | ~다 / ~이다 | med | all |
| ~에 있어서 | ~에서 / ~할 때 | high | formal |
| ~함에 있어 | ~할 때 | med | formal |
| ~에 다름 아니다 | ~다 / ~일 뿐이다 | med | academic |
| ~에 의해 | ~가 / ~로 | high | all |
| ~을 통해 | ~로 / ~으로 | high | all |
| ~에 대한 (남용) | ~의 / (생략) | high | all |
| 일컬어 ~라 한다 | ~라고 한다 | med | academic,wiki |
| 이른바 | (대부분 삭제) | med | news,academic |

## 4. "것이다" / "이러한" / "해당" 과다

영어 *such / these / the said* 직역과 AI 기본 마침법 "~인 것이다"가 한 문단에 여러 번 나오면 거의 확실한 AI 티.

| 나쁨 | 자연스러움 | 빈도 | 적용 도메인 |
|---|---|---|---|
| 사실 ~인 것이다 | 사실 ~예요 / ~다 | high | all |
| 문제인 것이다 | 문제다 / 문제예요 | med | all |
| 해야 하는 것이다 | 해야 한다 | med | all |
| 이러한 이유로 | 이 때문에 / 그래서 | high | all |
| 이러한 상황에서 | 이런 상황에선 | med | all |
| 이러한 사실은 | 이 사실은 | med | academic,news |
| 이러한 방식으로 | 이 방식으로 / 이렇게 | high | all |
| 해당 기능은 | 그 기능은 | high | b2b-message,wiki |
| 해당 시스템 | 그 시스템 | med | b2b-message,wiki |
| 해당 사항은 | 이 사항은 / 그건 | med | b2b-message,email |

## 5. 판에 박힌 개시 / 마무리

### 개시 문구 (대개 삭제가 정답)

- "안녕하세요! 오늘은~" → (바로 본론)
- "다들 궁금하셨을 텐데요~" → (삭제)
- "많은 분들이 ~하시는데요" → (자기 관찰로 — "나도 ~", "주위에서 ~")
- "~에 대해 알아보겠습니다" → (바로 내용)
- "~에 대해 살펴보도록 하겠습니다" → (바로 내용)
- "오늘 이 글에서는" → (삭제 / 한 줄 요약)
- "본격적으로 ~를 시작하기 전에" → (대부분 삭제)

### 마무리 문구

- "도움이 되셨길 바랍니다" → (삭제 또는 구체 후속)
- "궁금한 점이 있으시면 언제든지" → (삭제)
- "감사합니다!" (무조건 붙이기) → 상황에 맞을 때만
- "함께 ~해봅시다!" (강제 호응) → (삭제)
- "여러분의 ~을 응원합니다" → (대부분 삭제)
- "이상으로 ~을 마치겠습니다" → (그냥 끝)

### 외부 기여 / 제안 답변에서의 감사 표현

GitHub Issue / PR / 커뮤니티 제안처럼 외부 사람이 프로젝트에 관심을 보인 상황에서는 감사 표현을 지우지 않는다. 다만 한국어에서 "반갑습니다"는 주로 사람을 만나거나 소식을 접했을 때의 인사성 표현이라, **상대가 만들어준 결과물 / 도움 / 제안 자체**에는 "기쁩니다" 또는 "고맙습니다"가 더 자연스럽다.

| 어색함 | 자연스러움 | 메모 |
|---|---|---|
| 만들어줬다는 점이 반갑습니다 | 만들어줘서 기쁩니다 / 만들어주신 점이 고맙습니다 | 결과물에 대한 감정 |
| 관심 가져주셔서 반갑습니다 | 관심 가져주셔서 감사합니다 / 관심 가져주셔서 기쁩니다 | 감사가 더 직접적 |
| 외부 기여가 반갑습니다 | 외부 기여가 생겨 기쁩니다 | 프로젝트 관점 |
| 다시 한 번 정말 반갑고 고맙습니다 | 다시 한 번 감사합니다 / 고맙습니다 | 감사 반복 줄이기 |

**의도 확인이 필요한 경우**: 제3자 demo / SaaS / hosted service 제안은 "사용해달라"는 제안인지, "내가 만든 서비스를 공식 README에 연결하고 싶다"는 제안인지 다를 수 있다. 저장 정책, LLM provider, 공식/비공식 표기 같은 조건을 말하기 전에 **의도를 한 문장으로 확인**하면 답변이 덜 방어적으로 읽힌다.

예:
> 제가 이해한 방향이 맞는지 먼저 확인하고 싶습니다. 이 이슈는 프로젝트 사용자가 설치 전 체험할 수 있는 community demo를 제안하신 건가요, 아니면 별도 SaaS 형태로 운영 중인 서비스를 README에 연결하고 싶다는 제안에 가까울까요?

## 6. 수동태 / 모호한 주어 (Passive / Hidden Agents)

AI는 행위 주체를 숨기는 수동태로 도망간다.

| 나쁨 | 자연스러움 | 빈도 | 적용 도메인 |
|---|---|---|---|
| ~이 될 수 있습니다 | ~할 수 있다 | high | all |
| ~되어집니다 (이중 수동) | ~된다 | high | all |
| 고려되어야 합니다 | 고려해야 한다 / 챙겨야 한다 | high | formal |
| 요구됩니다 | 필요하다 / ~해야 한다 | med | formal |
| 활용되어 왔다 | 써왔다 / 자주 쓰였다 | med | academic,wiki |
| 평가되고 있다 | (누가) 평가한다 | med | news,academic |
| 인식되어 있다 | 알려져 있다 / (누가) 안다 | med | academic,news |
| 진행되어 왔다 | 해왔다 | med | news,academic |
| 주어진다 | (누가) 준다 | med | academic |
| 발견된다 | 보인다 / 나온다 | med | academic,news |

## 7. 불필요한 연결어 (Filler Connectives)

AI는 문장마다 "또한 / 뿐만 아니라 / 더불어 / 따라서"로 잇는다. 대부분 없어도 된다.

| 나쁨 | 자연스러움 | 빈도 | 적용 도메인 |
|---|---|---|---|
| 또한 ~할 수 있습니다 | (새 문장으로 시작, 연결어 삭제) | high | all |
| 뿐만 아니라 | (대부분 삭제) | high | all |
| 더불어 | (대부분 삭제) | med | linkedin,b2b-message |
| 나아가 | (대부분 삭제) | med | academic,b2b-message |
| 한편 | 진짜 대조할 때만 유지 | med | news,academic |
| 따라서 | 그래서 / (삭제) | high | academic,b2b-message |
| 그러므로 | 그래서 / 그러니까 | med | academic |
| 결론적으로 | 결국 / (삭제) | high | academic,blog |
| 즉 / 다시 말해 | (한 번만 / 삭제) | med | all |
| 아울러 | 그리고 / (삭제) | med | formal |
| 한마디로 | (대부분 삭제) | med | blog,newsletter |
| 요컨대 | 정리하면 / (삭제) | med | academic |

## 8. 과도한 parallelism / 3항 나열 강제

AI는 항목을 셋으로 맞추고 문장 길이를 균등하게 만든다. 의도적으로 흐트린다.

**나쁨**:
> 빠르고 정확하며 효율적입니다. 간단하고 명확하며 실용적입니다.

**자연스러움**:
> 빠르고 정확하다. 쓰기도 어렵지 않다.

| 나쁨 | 자연스러움 | 빈도 | 적용 도메인 |
|---|---|---|---|
| 기술, 인재, 자금의 세 가지 요소 | 기술이 필요해. 인력도, 돈도. | med | all |
| 첫째, ~. 둘째, ~. 셋째, ~. | 우선 ~. 그리고 ~. 마지막으로 ~. | high | academic,b2b-message |
| 안전하고 빠르고 저렴하다 | 안전하고 빠르다. 가격도 괜찮다. | med | marketing,review |
| 학습, 적응, 성장 | 배우면서 적응하고 자란다 | med | linkedin,blog |

## 9. 존댓말 레벨 불일치 (Honorific Mismatch)

같은 글 안에서 "합니다체"와 "해요체"를 섞거나, 전체 톤과 안 맞는 과격식을 넣는다.

- 캐주얼 포스트에 "~하시기 바랍니다" → "~해보세요" / "~하면 좋아요"
- 카톡/DM 톤에 "~하십니다" → "~해요" / "~합니다" 중 하나로 통일
- 친근한 인사 후 갑자기 "~하옵니다" → 톤 통일
- "하시는 분들께서는" → "하는 분들은" / "하시는 분들은"
- "가능하시다면" → "가능하면" / "되면"

### 9-A. 종결어미 톤 보존 (humanize 시 최우선 룰)

humanize 결과는 **raw의 종결어미 톤을 도메인 디폴트와 함께 결정**한다. "짧고 단단하게"를 핑계로 ~다체 글말체로 통일하지 않는다.

**도메인별 종결어미 디폴트**:

| 도메인 | 디폴트 어미 | ~다체 글말체 |
|---|---|---|
| 발화체 (YouTube / 팟캐스트 / 강의 / 라이브 인사말) | ~합니다체 / ~해요체 | ❌ **사용 금지** |
| 격식 글 (이메일 / 공문 / 비즈니스 메모) | ~합니다체 / ~드립니다 | ❌ raw 톤 strict 보존 |
| 캐주얼 (DM / 메신저 / 짧은 SNS) | raw 톤 그대로 (~해요체 / 반말) | ❌ raw 톤 보존 |
| 글말체 (블로그 / 에세이 / 책 / 마케팅 카피) | ~다 / ~한다 (글말체) | ✓ raw가 ~합니다체여도 ~다체 OK (블로그 표준) |

**한 글 내 어미 통일**: 어떤 도메인이든 한 글에서 어미가 섞이지 않게 한다 — raw에서 우세한 어미 군으로 통일한다.

**금기 패턴 (반드시 catch)**:
- 발화체 raw가 "~알아보겠습니다 / ~함께해 주세요 / ~거예요" 인데 humanized가 "~정리해본다 / ~팁이다 / ~달라진다" 로 가는 것 — 이건 카테고리 #9의 정면 위반이다.
- humanized 첫 문장이 ~합니다체 + 본문이 ~다체 + 마지막이 ~합니다체로 회귀하는 패턴 — 한 글 안에 두 어미군 동시 존재.

**예시**:

| Raw (발화체 YouTube) | ❌ 잘못된 humanize | ✓ 올바른 humanize |
|---|---|---|
| "오늘은 ~ 알아보겠습니다" | "오늘은 ~ 정리해본다" | "오늘은 ~ 정리해볼게요" |
| "~수 있을 거예요" | "~달라진다" | "~달라져요" |
| "그럼 시작하겠습니다!" | "시작합니다." (← 다른 문장은 ~다체인데 여기만 ~합니다체) | "시작할게요." |

## 10. 이모지 / 이모티콘 남발

포스트당 1~2개, 의미 있는 자리에만. AI는 섹션 헤더마다 🚀💡✨을 박는 경향.

- 섹션 헤더 / 불릿 앞 이모지 무한 반복 → 최대 1~2개만
- 문장 중간 이모지 → 대부분 제거
- 이모지로 강조 (🔥🎯) → 단어로 표현
- 마무리에 손/박수 이모지 (👏🙌) 자동 첨부 → 대부분 삭제

## 11. 단정 회피 / 과한 hedging

자기 글에 자신이 없을 때 AI가 자주 쓰는 방어막.

| 나쁨 | 자연스러움 | 빈도 | 적용 도메인 |
|---|---|---|---|
| ~일 수도 있습니다 (남발) | (아는 건 단언) | high | all |
| ~라고 할 수 있습니다 / ~라고 할 수 있다 | ~다 / ~이다 (단언) | high | academic,b2b-message |
| ~인 것 같습니다 (남발) | ~다 / ~예요 | high | all |
| 아마도 / 어쩌면 (반복) | (한 번만 살리기) | med | all |
| 제 생각에는 (과다) | (신념이 분명한 문장은 그냥 서술) | med | all |
| 어느 정도는 | (대부분 삭제) | med | academic,news |
| 일반적으로는 | (대부분 삭제 / 구체 사례) | med | academic,wiki |
| 대부분의 경우 | 보통 / 거의 (간결화) | med | all |
| 여러 가지 측면에서 | (구체 측면 나열) | med | academic,wiki |

## 12. AI 고빈도 어휘 (Korean LLM Vocabulary Tells)

2023년 이후 한국어 LLM 텍스트에서 유난히 자주 등장하는 단어들. 영어 *delve / tapestry / leverage* 의 한국어 짝.

| 나쁨 | 자연스러움 | 빈도 | 적용 도메인 |
|---|---|---|---|
| 일정상 | 일정이 생겨 / 일정 때문에 | med | chat,email |

## 부록: 적용 순서

1. **Brand voice** 가 있으면 최우선 적용한다. `preserve` 는 자동 치환보다 강하다.
2. **개인 금지어/선호어 리스트**가 있으면 다음으로 적용한다 (`examples/personal-list.md` 참고).
3. 입력의 도메인 / 우세 종결어미 / 보존 영역을 확인한다. 도메인 정보가 없으면 부록 E의 디폴트를 쓴다.
4. 부록 E의 도메인 우선순위에 따라 위 12 카테고리를 스캔하되, **high-confidence AI 티**만 고친다.
5. 학술 / 뉴스 / 이메일처럼 격식이 필요한 도메인은 딱딱함 전체가 아니라 **불필요한 격식**만 줄인다.
6. 채팅 / 리뷰 / YouTube 는 너무 매끈하게 만들지 않고 raw 의 말투, 생략, 감정 강도를 보존한다.
7. 한 문단에 3곳 이상 건드렸으면 멈추고 다음 문단으로 간다.
8. **전체 문장 수의 20%**를 넘으면 영향이 작은 변경부터 되돌린다. 1-3문장짜리 짧은 글은 최대 1문장만 고친다.
9. 출력 시 **다듬어진 전체 글** + **주요 변경 (최대 5개)** 형식. 변경이 5개 초과면 "+N개 더 — '전체 diff' 요청 시 모두 표시" 한 줄 추가.

## 부록 A. 연구 근거 (Research Findings)

이 카탈로그는 단순 관찰뿐 아니라 한국어 AI 탐지 연구의 정량 보고치와도 결이 맞다. 핵심 수치만 요약한다 — 전체 근거 / 평가 프로토콜 / 윤리 한계는 별도 위키 문서 [`korean-humanizer-research.md`](../korean-humanizer-research.md) 참조.

### A.1 KatFish — 쉼표 사용 패턴 (인간 vs LLM)

KatFish (2025) 가 한국어 에세이 / 시 / 논문 초록에서 보고한 쉼표 사용 차이. **카테고리 #7 (불필요한 연결어)** 와 같은 결을 가진 정량 근거.

| 장르 | 지표 | 인간 | LLM |
|---|---:|---:|---:|
| 에세이 | 쉼표 포함 문장 비율 | 26.31 | 61.03 |
| 에세이 | 평균 분절 길이 | 4.35 | 8.56 |
| 논문 초록 | 쉼표 포함 문장 비율 | 47.48 | 65.21 |
| 논문 초록 | 평균 분절 길이 | 9.07 | 11.55 |

→ 한국어 LLM 텍스트는 **쉼표를 더 자주 / 더 뒤에 / 더 긴 분절로** 쓴다. humanize 시 긴 쉼표 분절은 두 문장으로 쪼개는 편이 한국어답다.

### A.2 KatFish — 한국어 전용 punctuation 특징의 강도

| 장르 | 장르별 최고 baseline AUC | KatFish punctuation AUC |
|---|---:|---:|
| 에세이 | 81.27 | **94.88** |
| 시 | 66.02 | **73.10** |
| 논문 초록 | 57.33 | **75.62** |

→ 한국어에서 쉼표·종결어미·POS 다양성 같은 **언어 고유 특징**이 영어 모델식 일반 baseline 보다 평균 +19.78% 높은 AUC-ROC 를 보인다.

### A.3 XDAC — 짧은 비격식 텍스트의 별도 신호

뉴스 댓글처럼 짧은 텍스트에서는 **반복 자모 / 감정 기호 / 특수문자 / 비격식 표현** 의 결핍이 강한 신호다 (XDAC 댓글 탐지 98.5 % F1).

→ humanize 출력이 댓글 / 채팅 도메인일 경우 모든 매끈함을 다 깎아내면 오히려 비현실적이다. 카테고리 #9-A (종결어미 톤 보존) 와 결합해 도메인 디폴트로 판단한다.

### A.4 사람 판정의 한계 (LREAD / 사용자 실험)

- 한국어 인간 vs AI 에세이 식별 실험: 116 명 참가자 정답률 54.8 ~ 60.6 % (chance 근방).
- LREAD: 직관 정확도 0.60 → 루브릭 적용 후 0.90, 평가자 간 κ -0.09 → 0.82.

→ "사람이 보면 다 안다" 는 **거짓**이고, 동시에 자동 점수 하나로 사람을 판정해서도 안 된다는 뜻. humanizer 도 평가도 **다중 신호 + 사람 검토** 가 정답.

## 부록 B. 한국어 전용 feature schema (탐지·평가 보조용)

humanizer 는 *편집기*지만, 같은 신호를 *탐지/평가*에도 쓸 수 있다. 평가 자동화 / 회귀 테스트 만들 때 참조.

| 특징 | 측정 | 의심 방향 |
|---|---|---|
| 쉼표 포함 비율 | 쉼표 포함 문장 / 전체 문장 | 높을수록 LLM 의심 |
| 쉼표 평균 상대 위치 | 쉼표 위치 / 문장 길이 | 뒤로 갈수록 의심 |
| 쉼표 분절 길이 | 쉼표로 분리된 세그먼트 평균 길이 | 길수록 의심 |
| 명사 비율 | 명사 형태소 / 전체 형태소 | 높을수록 의심 (술어·어미 비율과 함께) |
| 술어·어미 비율 | 용언+어미 / 전체 형태소 | 낮을수록 의심 |
| 종결어미 엔트로피 | 문장말 어미 분포의 엔트로피 | 너무 낮으면 의심 |
| 어휘 다양성 (MATTR) | 형태소 기반 type/token | 낮을수록 의심 |
| 연결어 빈도 | "또한 / 따라서 / 즉 / 한편 / 뿐만 아니라" 빈도 | 높을수록 의심 |
| 비격식 표지 지수 | "ㅋㅋ / ㅎㅎ / ㅠㅠ / ?! / ..." 빈도 | 댓글·채팅에서 너무 낮으면 의심 |
| 종결어미 도메인 적합도 | 카테고리 #9-A 표 기준 | 발화체에 ~다체 글말체면 fail |

판정은 절대 임계가 아니라 **장르-조건부 z-score** 기준. 단일 신호로 판단하지 않고 상관이 낮은 신호 3 개 이상이 같은 방향이면 "검토 필요" 로만 올린다 (자동 단정 금지).

humanize 결과를 사람이 평가할 때 쓰는 5점 루브릭. README 의 Full Example, `examples/agent-vs-skill.md` 의 정성 평가가 이 축을 따른다.

## 부록 E. 도메인별 카테고리 우선 적용

각 도메인에서 가장 자주 작동하는 카테고리 순위. humanize 시 이 순서로 스캔하면 효율 ↑. 톤 디폴트는 raw 가 명시되지 않을 때 humanizer 가 가정하는 종결어미 / 격식 레벨.

| 도메인 | 1 순위 | 2 순위 | 3 순위 | 톤 디폴트 / 보존 |
|---|---|---|---|---|
| 블로그 (글말체) | #5 개시 | #1 강조어 | #4 것이다 | ~다체 자유 |
| 마케팅 카피 | #2 형용사 | #12 고빈도 어휘 | #1 강조어 | 임팩트 일부 보존 |
| 이메일 (격식) | #11 hedging | #6 수동태 | #3 번역체 | ~합니다체 strict |
| LinkedIn | #5 개시 | #1 강조어 | #10 이모지 | ~합니다체 + 친근 |
| YouTube 인트로 | #5 개시 | #11 hedging | #1 강조어 | ~해요체 (~다체 금지) |
| 뉴스레터 | #5 개시·마무리 | #7 연결어 | #1 강조어 | 캐주얼 ~해요체 |
| 위키 | #3 번역체 | #6 수동태 | #4 것이다 | 학술 격식 일부 보존 |
| **학술 초록** *(NEW v0.7)* | #3 번역체 | #6 수동태 | #4 것이다 | "사료된다 / 시사한다" 일부 살림, 정형 문구 ("본 연구 / 다음과 같다") 보존 |
| **뉴스** *(NEW v0.7)* | #6 수동태 | #1 강조어 | #11 hedging | 객관 격식 strict, 보도 정형 ("밝혔다 / 알려졌다 / 전했다") 보존, 인용문 글자 단위 동일 |
| **카톡·DM** *(NEW v0.7)* | #1 강조어 | #10 이모지 | #11 hedging | ~해요체 / 반말 strict, 첫 인사 친근 표현 1 회 보존, 이모지 0-1 개 (3+ → 1) |
| **제품 리뷰** *(NEW v0.7)* | #2 형용사 | #1 강조어 | #12 고빈도 어휘 | 솔직 톤 살림, 별점·구매일·제품명 strict, 단점 표현 부드럽게 안 함 |
| **B2B 메시지** *(NEW v0.7)* | #11 hedging | #3 번역체 | #5 마무리 | ad-hoc 격식 (~합니다 + ~할게요 혼합), 호명·일정·금액 strict, 이중 존경 1 단계 완화 |

### 사용 가이드

- **"이 도메인에서는 이 카테고리만"** 이라는 뜻이 아니다. 1-3 순위는 **가장 자주 작동하는** 패턴 — 12 카테고리 모두 후보로 두고 순서로 우선 스캔.
- **톤 디폴트** 는 raw 입력에 도메인 정보가 없을 때 humanizer 가 가정하는 값. 사용자가 "유튜브 인트로야 / 학술 abstract야" 같이 명시하면 그 값 우선.
- **금지 변경 영역** 은 도메인마다 다르다 — `examples/domain-*.md` 파일 각각의 메타데이터 표 참조.
- **brand voice / personal list** 가 있으면 톤 디폴트보다 우선 — 사용자 자기 톤이 도메인 평균보다 강한 신호. 적용 순서는 brand voice (방식 D) → personal list (방식 A/B/C) → 카탈로그. 자세한 방식은 [SKILL.md / PROMPT.md "방식 D"](../SKILL.md), 템플릿은 [`examples/brand-voice-template.md`](../examples/brand-voice-template.md).

## 부록 F. 도메인 코드 표준

카탈로그의 4 번째 컬럼 "적용 도메인" 에 들어가는 값의 표준. 도메인 컬럼 lint (`scripts/lint-patterns.sh` v2) 가 이 목록을 valid 값 셋으로 사용한다.

### 12 도메인 (개별 코드)

| 코드 | 의미 | 디폴트 어미 |
|---|---|---|
| `blog` | 블로그 / 브런치 / 워드프레스 글말체 | ~다체 / ~한다 |
| `marketing` | 마케팅 카피 / 랜딩 페이지 / 광고 | 임팩트 보존 |
| `email` | 격식 이메일 / 공문 | ~합니다체 strict |
| `linkedin` | LinkedIn 포스트 / 코멘트 | ~합니다체 + 친근 |
| `youtube` | YouTube 스크립트 / 인트로 (발화체) | ~해요체 (~다체 금지) |
| `newsletter` | 뉴스레터 / 구독 메일 | 캐주얼 ~해요체 |
| `wiki` | 위키 / 백서 / 문서 | 학술 격식 일부 보존 |
| `academic` | 학술 초록 / 논문 도입 | ~다체 + 정형 어휘 |
| `news` | 뉴스 보도 / 기사 | 객관 격식 strict |
| `chat` | 카카오톡 / DM / 메신저 | ~해요체 / 반말 |
| `review` | 제품 리뷰 / 평점 코멘트 | 솔직 톤 |
| `b2b-message` | B2B 비즈니스 메시지 / 제안 | ad-hoc 격식 혼합 |

### Shorthand (약식 코드)

빈출 도메인 그룹은 이름을 줘서 표를 읽기 쉽게 한다.

| Shorthand | 풀어내기 (= 다음 도메인 모두) |
|---|---|
| `all` | `blog, marketing, email, linkedin, youtube, newsletter, wiki, academic, news, chat, review, b2b-message` (12 개 전체) |
| `informal` | `chat, review` |
| `formal` | `email, b2b-message, academic` |

### 컬럼 값 작성 규칙

1. **전 도메인 패턴** → `all` 단독 사용. (예: 카테고리 #4 "사실 ~인 것이다" — 모든 도메인에서 AI 티)
2. **2-3 도메인에 강하게 치우친 패턴** → 도메인 코드를 **콤마로** 연결. (예: `marketing,review` — 공백 없이 / 공백 있어도 lint 통과)
3. **shorthand 가 정확히 맞을 때만** 약식 사용. (예: `formal` 은 정확히 `email,b2b-message,academic` 일 때. `email,academic` 같이 부분 셋이면 콤마 표기.)
4. **혼용 금지**: 한 셀에 `all` 과 다른 코드를 같이 쓰지 않는다. `all` 은 단독 / 다른 모든 코드와 배타적.
5. **shorthand 와 개별 코드 혼합** 도 가능. 예: `formal,marketing` = `email,b2b-message,academic,marketing`. lint 가 풀어서 검증.

### 신규 도메인 추가 시

새 도메인 (예: `podcast`, `lecture`) 을 추가하려면:

1. 이 부록 F 의 "12 도메인" 표에 행 추가 + 디폴트 어미 명시
2. `scripts/lint-patterns.sh` 의 valid 도메인 셋에 새 코드 추가
3. 부록 E 의 우선순위 매트릭스에 새 도메인 행 추가
4. `examples/domain-<new>.md` 사례 추가
5. 카탈로그의 카테고리 표 중 새 도메인에 specific 한 행은 도메인 컬럼에 새 코드 부여 (선택, 첫 PR 에선 모두 `all` 유지 OK)

새 도메인 추가는 v0.8 → v0.9 같은 minor bump 가 자연스럽고, 카테고리 #13 추가는 major bump 동반 (v1.0 → v2.0).

## 부록 D. 윤리·한계

- 이 카탈로그는 **편집 보조 / 연구용 분석** 목적이지, 사람 글을 자동으로 "AI 가 썼다" 고 판정하는 도구가 아니다.
- 단순한 문체, 학습자 문체, 짧은 글은 단일 신호로 보면 AI 로 오탐될 수 있다 (영어권 비원어민 오탐과 같은 결).
- humanize 는 **사실 보존 + 출처 보존** 우선. 무근거 세부 추가 / 사칭 / 평가 우회 목적 사용은 지원하지 않는다.
- 법률 / 의료 / 보안 / 재무 텍스트는 비격식 변환 / 생략을 원칙적으로 금지 (SKILL.md / PROMPT.md 의 절대 규칙과 동일).
