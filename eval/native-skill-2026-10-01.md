## 기존 실제 호출에서 발견한 문제

Opus 이메일에 “변경해야 하게 되어”가 나왔고 일부 요청에서 카탈로그를 읽지 않았습니다. Astra의 사실 안내·GitHub 답변에는 필수 제목이 빠졌습니다. Opus의 변경 설명은 원문에 없는 사건 순서를 가정하기도 했습니다. 지침을 직접 전달했던 이전 검사만으로 native 호출 품질을 설명할 수 없었습니다.

참조 파일 읽기를 완료 조건으로 만들고, 겹치는 동사 표현·평가 정도·가능성과 경험의 구분을 스킬 내부에서 대조하도록 보완했습니다. 출력 계약을 앞부분으로 옮겼고 변경 이유에도 원문 근거를 요구했습니다. 중간 후보의 이메일 제목 누락을 발견해 지침을 다시 보완했습니다. 최종 응답은 그 뒤 입력당 한 번 실행한 결과이며 수동으로 고치지 않았습니다.

독립 검토에서 확신을 효과의 양으로 바꾸거나 성능 평가를 낮추고, 등장 횟수를 잘못 설명한 응답이 확인됐습니다. 확신·평가 강도의 보존을 명시한 뒤 채팅·리뷰·GitHub 답변을 두 모델에서 다시 실행했습니다. 나머지 18개는 `da6c68c` 소스의 실제 첫 응답이며 실행별 소스 커밋·해시를 JSON에 구분했습니다. 중간 GitHub 제목 누락도 진단 기록에 남깁니다.

## 수동 예시 검토

- 이전 마케팅 답안의 “혁신적인 → 새로운”은 신규성을 추가합니다.
- 리뷰 답안의 “사용 가능합니다 → 씁니다”는 실제 사용 경험으로 바꾸고 사용 환경 범위도 누락합니다.
- GitHub 답안은 첫 기여 사실을 빼고 원문에 없는 운영 질문을 넣었습니다.
- 채팅의 “3개 이상 → 1개, 0개로 깎지 마라”는 현재 역할 기준과 다릅니다.
- 뉴스 답안은 업계가 부여한 “의미 있는” 평가를 빼고 이를 기자의 평가라고 설명했습니다.

마케팅·채팅·리뷰·GitHub 답안은 실제 응답으로 교체했고, 뉴스는 현재 기준의 답안으로 사용하지 말라는 설명을 붙였습니다. Brand voice 예시는 의미 보존이 상위 규칙이지만 개수·위치 정책만 읽으면 감정·상태 표시를 지울 여지가 있습니다. 프로필 정책도 의미 보존 범위에서 적용해야 합니다.

## 확인과 한계

최종 기록 24개 모두 카탈로그 읽기, 필수 제목, 최대 5개 변경 목록과 첫 응답 안내를 확인했습니다. 원본 응답과 저장된 문자열·SHA-256도 24개 모두 일치합니다. 독립 검토에서는 원문과 응답·변경 설명을 대조해 확정 결함 0건을 보고했습니다. 날짜·금액·링크·상태값·조건과 명시적인 이모지 유지 요청에서 확정적인 의미 변경을 찾지 못했습니다. 이는 이 입력·실행에 대한 검토 결과이며 일반적인 품질 성공률이 아닙니다. 원문의 감정·상태 구분이 문장으로 남는다면 이모지 삭제만으로 실패로 판정하지 않습니다.

리뷰의 배터리 어순과 B2B의 가능성·가격 표현은 더 직접적으로 다듬을 여지가 있으나 해당 문맥에서 확정적인 의미 변경으로 판정하지 않았습니다. 원본 응답은 그대로 남겼습니다.

이는 프로젝트 스킬의 실제 발견·호출·참조 읽기 검사입니다. ZIP 압축 해제부터 새 사용자 설치까지의 전체 경로, 긴 글·다른 모델·반복 실행의 성공률은 검증하지 않았습니다. 스킬 지침은 모델의 매번 동일한 응답을 보장하지 않습니다. 고정 fixture 검사와 모델 품질 성공률은 구분합니다.
